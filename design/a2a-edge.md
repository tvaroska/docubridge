# A2A Edge (agents)

> The Bridge's agent-facing front door — an A2A server for Path-A partner/carrier agents and the internal servicer agent.

**Surface.** The edge speaks **canonical A2A** — JSON-RPC 2.0 on the standard `a2a-sdk`, per the "as standard as possible" principle ([adk](adk.md)). No bespoke REST dialect. This edge **is [Ring 1](../spec/standards.md)** — the standardization priority's outermost, most-protected layer; the D1–D5 wire disciplines (canonical envelope, domain-inside-parts, lifecycle, durable task, two-owner split) are written up there.
- Spec operations: `message/send`, `message/stream`, `tasks/get` / `tasks/list` / `tasks/cancel` / `tasks/resubscribe`, with A2A `Message` / `Task` / `Artifact` / `Part` on the wire. The domain types (`CollectRequest`, `ExchangeTurn{CollectionStatus}`, `RequirementsList`, `LedgerEntry`) travel as the payload carried **inside** A2A parts/artifacts — the domain contract is unchanged; the envelope is standard.
- Dynamic **Agent Card** at the well-known discovery location, generated from installed skills' `name`/`description` ([Agent Skills format](skills.md)) — the progressive-disclosure discovery layer — so a live skill-add regenerates it with no redeploy.
- **Streaming** via `message/stream` / `tasks/resubscribe` (SSE per spec) for long-running tasks (status + artifact events, keepalives).
- Task lifecycle, **artifact versioning** (each version is a new artifact on the same task), pluggable persistence, and concurrency-safe cancellation of active tasks.

**Inbound fulfillment.** A party responds on the A2A edge with the exchange's context token (Path A: a structured data response), or via the portal (Path B). The **pull spine** is the core motion — a party responds **inbound** to an already-open exchange, so the *pull path itself* needs no A2A client: the party is handed the link/context out-of-band. **Outbound is nonetheless first-class** ([outbound direction](outbound.md)): the Bridge also runs an **A2A client** for chases, deliveries, and dialing counterparties (Agent-Card discovery). That client (`bridge/outbound.py`, over the A2A-client seam) carries party-channel nudges (SLA-ladder steps and the operator's manual chase), Deliver (`Delivery`, CUJ-3) and dial-out (`DialOut`, the Benefits carriers, CUJ-12).

**What the Bridge sends back.** The deliverable to the servicer's agent is an **`ExchangeTurn`** carrying a **`CollectionStatus`** — the **classified ledger**: a tuple of `LedgerEntry` (doctype · disposition · canonical issuer · key fields), plus a best-effort "still outstanding" and a `terminal` flag. Accepted documents appear as **[artifact references](artifacts.md)** (a `FileWithUri` handle), not bytes — the agent fetches bytes on demand from the scoped endpoint. Disposition maps to A2A task status the ordinary way (`_status_for`: `ExchangeTurn.terminal=False` → `INPUT_REQUIRED`, otherwise `COMPLETED`), so **the app reads standard A2A task status + a ledger projection — never ADK events.** That `INPUT_REQUIRED` is exactly the **resumable park signal** a native [consumer](a2a-consumer.md) (`RemoteA2aAgent`) turns into a zero-compute `LongRunningFunctionTool` pause — the edge emits it as a first-class part of the contract. The internals are a **hybrid**: the deterministic `Collector` for structured traffic, the `document_bridge` [LlmAgent + tools](adk.md) for intent, HITL park and review resumes; what crosses this edge is the domain contract plus an additive artifact reference. See [disposition](disposition.md) for how each entry's verdict is set.

**Hybrid edge — a deterministic front door, the LlmAgent for intent.** The agent-facing executor routes behind `BRIDGE_EDGE_MODE=deterministic|hybrid` (unset/blank → deterministic; any other value → ValueError at app build). In deterministic mode the LLM leg is never constructed; structured traffic stays model-free. Route table (first match wins):

| # | Match | Leg | Wire outcome |
|---|---|---|
| G | Message on an existing INPUT_REQUIRED task whose LLM session holds an unanswered request_human_review call | guard | a HumanReviewResolution part → R6; anything else refused (InvalidRequestError), task unchanged, zero compute |
| R1 | A data part validating as ExtractionResult (classify_path → Path.A) | patha validate-only | terminal turn, COMPLETED; a Path-A hitl_review stays pending-terminal (never hands off, model-free in both modes) |
| R2 | A CollectRequest data part and/or ≥1 by-reference file part | Collector | SUBMITTED → COMPLETED; LLM invoked 0 times |
| R3 | R2's turn has ≥1 entry with gate=hitl_review and the process skill declares bridge-hitl: park | Collector → LLM handoff | after persist + URI rewrite, handed to the LLM leg, which calls request_human_review per hitl entry → INPUT_REQUIRED, terminal=False |
| R4 | Text-only (no CollectRequest, no file part, no resolution) — on a new task, or on an INPUT_REQUIRED task with no pending review | LLM leg | per mapping below (deletion / off-script reject / escalate / unrouted) |
| R5 | A HumanReviewResolution part on a task with no pending review | — | InvalidRequestError (no_pending_review) |
| R6 | A HumanReviewResolution whose call_id matches the pending call, from an authorized reviewer principal | LLM leg resume | fresh Runner, id-matched FunctionResponse → WORKING → COMPLETED with the resolved entry, or INPUT_REQUIRED while other reviews pending. call_id mismatch → InvalidParamsError; non-reviewer → InvalidRequestError; task unchanged in both refusals |

**R2 for the RFP process — the RFP opener.** When the runtime binds an RFP board (`BRIDGE_RFP_PROCESS`; `build_a2a_app(rfp_board=…)` or `bridge/edge/rfp_open.py::rfp_board_from_env`), a `CollectRequest` whose `process` the board serves skips the Collector: the board's home process (`BRIDGE_RFP_PROCESS`), or any emergent-Collect process skill installed live in the registry (`RfpBoard.serves` → `bridge/edge/skills.py::rfp_policy_for`, a registry read per request). Each RFP is opened and projected with its own process's policy; a request of another process on an existing RFP id is refused. The process is checked after `decode_intake`, in both edge modes, and the route is model-free. The request opens or updates the emergent-Collect RFP on the durable board through `open_or_update_rfp`, which runs read → apply → put whole on one worker thread because the board's compare-and-set versions are thread-local:
- **Identity.** `rfp_id` = `request.context_id`, else the A2A context. It must match `RFP_CONTEXT_RE` because it is the `/rfps/{rfp_id}` path segment and the reply token's HMAC input.
- **Open, update or read.** An absent RFP is opened. A present RFP with requirements gets `update_requirements`, which writes nothing when the list is identical. A present RFP without requirements is a status read. A changed `due_at` is ignored.
- **Reply.** The turn is the RFP's `ExchangeTurn`: every carrier × line cell, non-terminal → `INPUT_REQUIRED`, with `context_id` = the RFP id.

Every refusal is raised before any task event, so on a new task it is a JSON-RPC error:
- an inline or URL file part → InvalidParamsError `rfp_submissions_unsupported` (quotes arrive by email or the carrier checklist);
- a bad context id → InvalidParamsError `invalid_rfp_context`;
- an invalid open or update (no requirements or `due_at` on open, a party-less or duplicate item) → InvalidParamsError `invalid_rfp_request: <reason>`;
- an exhausted compare-and-set retry → InvalidRequestError `rfp_changed_concurrently`.

Like any `execute`-time refusal, one sent with an existing `task_id` marks that task FAILED (see the pre-dispatch guard below). Every other process keeps plain R2. With no RFP board bound, the edge behaves exactly as without the opener.

Per-process opt-in (D5): skill frontmatter bridge-hitl: park | report (default report). report = the Collector's pending/hitl_review entry rides a terminal turn and the consumer owns review (Aon conformance record B stays COMPLETED with 0 LLM calls in hybrid mode). park = the Bridge owns review and parks on the native LRFT (Address hitl_review records park and reach timeline.json hitl_resolved).

Ledger-from-tool-responses rule (D4): project_turn_from_events reads only function_response parts of run_disposition_gate, request_human_review, handle_deletion_request, reject_submission, escalate_submission, plus the executor-fed resolution response. Model text parts are never relayed. accepted comes only from a run_disposition_gate auto_approve response (args pinned by a before_tool_callback from extraction signals) or a reviewer resolution.

**Gate pinning.** The `document_bridge` LlmAgent may call `run_disposition_gate` but never supplies its inputs. The root agent's `before_tool_callback` (`bridge/gatepin.py::pin_gate_args`) overwrites all five gate arguments — `doctype`, `candidate_doctypes` (the label space), `legible`, `overall_confidence`, `flagged_fields` — from signals recorded in session state: `extract_document`'s genuine `ExtractionResult` (recorded inside the extraction sub-agent and forwarded to the parent session by the AgentTool's state-delta forwarding; same flagged-field fallback and issuer canonicalization as the Collector), or the Collector's signals seeded before the invocation. Neither the model's call args nor the `extraction_agent`'s text response is ever a source. The most recently recorded un-gated record is consumed once per gate call; re-recording a doc_id (a resubmission) makes it gateable again. With no un-gated record, or no label space, the call is refused with a Bridge-authored `{"refused": true, reason_code, message}` (`gate_signals_missing` / `label_space_missing`) that never validates as a verdict. The pin (call id → doc_id + the exact signals) rides the gate response event's `actions.state_delta`; the projection mints a gate entry only from a pinned response whose verdict equals the gate recomputed over the pinned signals, with doc_id/doctype/issuer taken from the pin. Reading that Bridge-authored callback output is not reading model content; an unpinned or inconsistent gate response mints nothing. The label space is Bridge-decided: on R4 it is the process the deterministic text resolver (`parse_text_request` + the skill's candidate doctypes) finds in the message — none found, none set, every gate call refused; an R3 Collector seed carries its request's label space.

LLM-outcome → wire mapping (D6): status.message text is always Bridge-authored (a tool's message or summarize_turn), never model text. reason_code / review_call_id ride status.message.metadata (envelope extension space).

| Function response | LedgerEntry | terminal → task state | lifecycle | status.message.metadata |
|---|---|---|---|---|
| run_disposition_gate (pinned) | entry projected from the verdict | auto_approve/resubmit/unsupported → terminal; hitl_review routes to request_human_review | on_track | — |
| request_human_review (LRFT, pending) | the Collector's hitl entry with disposition=pending, gate=hitl_review, reason_code=awaiting_human_review | False → INPUT_REQUIRED | on_track | reason_code=awaiting_human_review, review_call_id=<call id> |
| executor-fed resolution (id-matched) | the Collector's original hitl entry transformed as bridge/pathb.py::resolve_hitl does | True → COMPLETED unless other reviews pending | on_track | reason_code=entry's reason_code |
| handle_deletion_request | none (erasure is not a disposition) | True → COMPLETED | on_track | reason_code=deletion_completed OR nothing_to_delete |
| reject_submission | none | True → COMPLETED | on_track | reason_code=off_script_rejected |
| escalate_submission | none | False → INPUT_REQUIRED, survives tasks/get | escalated | reason_code=escalated_for_review |
| no tool response (model text only) | none | True → COMPLETED | on_track | reason_code=off_script_unrouted |

Session keying (D9): LLM-leg ADK session = (app_name="document_bridge", user_id=<party>, session_id=<A2A context_id>), where party = CollectRequest.party when present, else the context's owning party resolved from the shared artifact store (_candidate_users), else "_unscoped". So handle_deletion_request erases exactly the artifacts the Collector saved for that context (addressing = isolation, [zones](zones.md)).

Erasure stays inside the session's own keys: `handle_deletion_request` deletes only a filename listed under exactly `(document_bridge, party, context_id)`, all versions at once, so the scoped fetch URI 404s afterwards. A filename in ADK's user namespace (`user:` prefix), which spans every context of a party, is never erased. A deletion addresses the context named by the turn's `context_id` (the first path segment of the scoped fetch URI). When more than one party owns that context, nothing is erased. The final status message of every LLM-leg outcome carries `metadata.reason_code` per the outcome table (a gate-only turn carries none; a turn where no tool ran carries `off_script_unrouted`).

Contract delta (D10): only an additive contract.HumanReviewResolution (extra="forbid", call_id, resolution, message, reviewer). ExchangeTurn, CollectionStatus, LedgerEntry, CollectRequest unchanged. Reviewer authorization comes from the A2A call-context principal (RequestContext.call_context.user), never from the payload.

**HITL park/resume as built (G/R3/R6).**
- *Park (R3).* `request_human_review` returns `None`, which is what pauses an ADK LongRunningFunctionTool: the call event carries `long_running_tool_ids` and has no response, and the invocation stops with zero compute. The R3 handoff runs on the artifact session key (`party`, the turn's `context_id`). It seeds the leg with the Collector entries, the request's label space and one `source="collector"` recorded signal per hitl entry; the genuine `ExtractionResult`s come from `Collector.collect(results_out=...)`, never a re-extraction. The Collector's original entries are persisted in session state under `bridge:review_tasks[<task_id>]`. The handoff text is Bridge-authored (`Human review required for: <doc_id> (<reason_code>).`). If the model parks nothing, or the leg fails, the edge finishes exactly as report mode would (the Collector turn, COMPLETED).
- *Per-task scoping.* At park the executor writes server-authored `task.metadata.bridge_review_session = {user_id, session_id, call_ids}` through `TaskUpdater.update_status`, always as the full value (`MergeFrom` replaces top-level keys). Client request metadata never reaches `task.metadata`. Pending-for-task = the task's `call_ids` ∩ the session's unanswered review calls. A call parked on another task of the same context is therefore never resolvable here. Reading this pending set is a session-service read: it never builds a Runner and never calls the model.
- *Pre-dispatch guard.* Every refusal is raised by `CollectExecutor.admit`, called from `EdgeRequestHandler` (`message/send` + `message/stream`) before the SDK touches the task. Refusals: G (`awaiting_human_review`), R5 (`no_pending_review`) and R6 validation. An exception raised inside `AgentExecutor.execute` would mark the existing task FAILED. `execute` repeats the checks as defense in depth, so two identical resolutions racing past the guard can still fail the task.
- *R6 validation, in order.*
  1. The tagged part decodes through the tolerant reader; otherwise `InvalidParamsError` `malformed_human_review_resolution`.
  2. The call-context principal is an authorized reviewer; otherwise `InvalidRequestError` `reviewer_not_authorized`. This check comes before the id check, so id validity never leaks to a non-reviewer.
  3. `call_id` is pending on this task; otherwise `InvalidParamsError` `review_call_id_mismatch` (JSON-RPC -32602) — a wrong, already-answered or other-task id. ADK itself raises on an unknown id and re-accepts an answered one, so this check is the edge's.
- *Reviewer authorization.* The allow-list comes from `build_a2a_app(reviewers=...)`, else `BRIDGE_EDGE_REVIEWERS`. It fails closed: unset or empty refuses every resolution. The principal is the authenticated A2A call-context user. It is populated by an injected Starlette `AuthenticationBackend` (`build_a2a_app(auth_backend=...)`); the edge ships none, so a deployed edge refuses all resolutions until a verified principal source is wired. The payload `reviewer` is an audit label only. The a2a-sdk task store scopes tasks by owner principal: a principal other than the task's owner cannot see the task at all (`TaskNotFoundError`). The resolving principal is therefore the owner's — the consumer agent relays its human reviewer's decision.
- *Resume (R6).* A fresh Runner over the durable session receives the id-matched `FunctionResponse` as `role="user"` content and continues the parked invocation (same `invocation_id`). The turn is rebuilt from the persisted Collector entries:
  - a resolved target is `resolve_hitl`-transformed (disposition, reviewer message; gate and gate reason kept);
  - a still-pending target keeps the paused overlay;
  - the resume's own events are projected on top.
  The rebuilt turn replaces the task's `exchange_turn` artifact (same artifact id). Reviews remaining → INPUT_REQUIRED with the next `review_call_id`. None remaining → COMPLETED, with the reviewer's message and the resolved entry's reason code. Several reviews of one turn resolve one at a time: a resume of one of several paused calls yields no events until the last is answered.

**Lifecycle per leg (D3/D4).** Two [Ring 1](../spec/standards.md) disciplines are now leg-specific:
- **D3 — leg-specific WORKING.** Deterministic legs (R1/R2) emit SUBMITTED → COMPLETED (no intermediate WORKING — the Sense-A collect completes synchronously in one call, so there is no genuine in-connection work phase). The LLM leg emits SUBMITTED → WORKING → COMPLETED | INPUT_REQUIRED (resume: WORKING → …) — the model call is genuine in-connection work, so WORKING is honest there. Every status update keeps a non-empty status.message.
- **D4 — one-durable-task honored on the LLM leg, not the deterministic completing path.** On the LLM leg the single-durable-task discipline is honoured in full: a HITL park or escalate is one durable task that parks and resumes on the same task_id/context_id, the ADK session durable via the sessions seam and ResumabilityConfig(is_resumable=True) on the edge App. On the deterministic completing path each round genuinely completes, so a new task per round under the same exchange context_id remains correct (the context_id is the aggregate).

**Long-running tasks (days → weeks).** An A2A task is a durable server-side resource with **no built-in TTL** — a collection can legitimately stay `WORKING`/`INPUT_REQUIRED` for weeks. Nobody holds it open: the task is persisted and woken only by a party turn, a [clock alarm](proactive.md), or an HITL resume. Clients learn of progress without a held connection via `tasks/get` (poll), `tasks/resubscribe` (re-attach after disconnect), and push-notification webhooks for state changes. See [long-running collection](long-running.md) for the full model and the durability substrate.

**Programs (multi-party fan-out).** Each leg is its own context + party — competitors never share a context (isolation by per-leg addressing, not UI filtering). A provider-facing program context links the legs and carries the rollup.

**Request intake — format vs capability (decided; as-built).** The structured `CollectRequest` JSON `DataPart` is the primary intake shape. A natural-language (`text/plain`) request is accepted on the same axis as the [dual-path](dual-path.md) shape: a process skill advertises **one `AgentSkill` with two `input_modes` (`application/json` + `text/plain`), routed by content**, with a free-text part parsed into a `CollectRequest` — **not** a second per-format `AgentSkill`, because A2A skills are discovery metadata (a capability axis), not addressable routes, and a format split would multiply the process-keyed skill taxonomy. This keeps input *format* on `input_modes` + content routing, orthogonal to the *capability* axis ([Ring 1](../spec/standards.md) D2/D3). Free-text-from-a-human belongs to the [A2UI](a2ui-edge.md) party edge.

The dual `input_modes` advertisement lives in the skill metadata (`SkillMeta.input_modes`, `bridge/edge/skills.py`) and feeds the dynamic Agent Card (`bridge/edge/card.py`); content routing is `bridge/edge/intake.py:decode_intake` (structured JSON wins when both are present, else text falls back). On the deterministic edge text + files → parse_text_request → Collector; on the hybrid edge a text-only message is routed to the LlmAgent as an intent (R4), not parsed into a CollectRequest.
