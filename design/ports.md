# Managed-Service Ports

> Every managed-service boundary is a **port** with **two adapters**, selected by config: a **local adapter** (fast dev/test) and a **GCP adapter** (deployed). Built together, not local-first-then-swap.

The ports are **[Ring 2](../spec/standards.md)** — the standardization priority's portability contract. Typed against the *real* platform ABCs so the mock→real / local→GCP swap is a no-op for the agent; custom here is tolerated only as an *adapter behind the ABC*, never a divergent interface.

| Port (`bridge/ports/`) | Local adapter | GCP adapter |
|---|---|---|
| **Sessions** (`sessions`) | ADK `DatabaseSessionService` on async sqlite (in-memory when no DSN) | ADK `VertexAiSessionService` on Agent Engine when `BRIDGE_AGENT_ENGINE_ID` is set (or `DatabaseSessionService` on Cloud SQL Postgres when unset) |
| **Task store** (`task_store`) | local embedded store | a managed relational store, adoptable as the platform's managed task store via a one-adapter swap |
| **Exchange store** (`exchange_store`) | local embedded store | a managed relational store |
| **Skill registry** (`skill_registry`) | directory of [Agent Skills](skills.md) folders | GCP Skill Registry (same [Agent Skills format](skills.md)) |
| **Memory bank** (`memory_bank`) | ADK `InMemoryMemoryService` (or `SqliteMemoryService` when `BRIDGE_MEMORY_DB_PATH` is set) | ADK `VertexAiMemoryBankService` on Agent Engine (`BRIDGE_AGENT_ENGINE_ID`) |
| **Scheduler/Timer** (`scheduler`) | in-process, virtual clock | Cloud Tasks |
| **A2A client (outbound)** (`a2a_client`) | injected fake transport | authenticated transport with Agent Identity |
| **Extraction** (`extraction`) | fixture extractor (deterministic) | Gemini *or* Gemini + Document AI pre-pass — engine-selectable |
| **Email ingress** (`email_ingress`) | a landing directory of `.eml` + attachments + processed markers | a GCS landing bucket, same object layout, create-only writes |
| **Audit vault** (`audit_vault`) | `LocalAuditVaultStore` (in-memory / filesystem write-once WORM lock) | `GcpAuditVaultStore` on 7-year retention-locked Cloud Storage (`BRIDGE_VAULT_BUCKET`) |
| **Operational store** (`operational_store`) | `InMemoryOperationalStore` / `SqlOperationalStore` on SQLite | `SqlOperationalStore` on AlloyDB / Cloud SQL Postgres (`DATABASE_URL`, refuses in-memory fallback) |
| **Action inbox** (`action_inbox`) | `InMemoryActionInboxStore` / `SqlActionInboxStore` on SQLite | `SqlActionInboxStore` on AlloyDB / Cloud SQL Postgres (`DATABASE_URL`, refuses in-memory fallback) |
| **Agent Gym** (`agent_gym`) | `InMemoryAgentGymEngine` / `SqlAgentGymEngine` on SQLite | `SqlAgentGymEngine` on AlloyDB / Cloud SQL Postgres (`DATABASE_URL`, refuses in-memory fallback) |
| **Knowledge catalog** (`knowledge_catalog`) | `InMemoryKnowledgeCatalog` / `SqlKnowledgeCatalog` on SQLite | `SqlKnowledgeCatalog` on AlloyDB / Cloud SQL Postgres (`DATABASE_URL`, refuses in-memory fallback) |

**The config knob** selects a global port mode (local or deployed) with per-port overrides, so you can move one boundary onto a managed service at a time. The **same test suite runs against both** adapters — that parity is what lets the Bridge develop at local speed while genuinely running on the managed platform it showcases.

**Why ports outlast the demo.** The Agent Platform and the A2A protocol are still moving — capabilities that need a self-owned store today become managed services tomorrow. The A2A **task store** is the example: it is backed by a store the Bridge runs, and as the platform matures into a managed task store, adopting it is a **one-adapter swap** with the shared test suite proving behavior didn't change. The port is how the Bridge rides platform evolution without a rewrite — a property a real product needs, not just a demo. The same holds per boundary, so the Bridge can move onto each new managed service the day it lands.

**Why the task-store GCP adapter must be a shared store (the session-affinity trap).** The A2A edge protocol is `POST message:send` then poll `GET tasks/{id}` to a terminal state — two requests that must see the same task. On any multi-replica GCP substrate **without session affinity** (Cloud Run with `>1` instance, or any multi-replica managed agent runtime), an in-process task store is per-replica: the write and the poll land on different replicas and the poll 404s until the client's deadline. This is not hypothetical — a peer A2A-on-GCP reference (`weimeilin79/vibeflix-audit`) measured an **86.8% 404 miss rate** with the stock `InMemoryTaskStore` on Agent Runtime, and a full run dropped from ~5m to ~1m44s once every replica read/wrote a single shared store. Our GCP `task_store` adapter is Cloud SQL (a shared relational store) precisely so cross-replica read-after-write holds; the local adapter is single-process so the trap never manifests there. The parity claim is tested by `tests/test_durable_ports.py::test_task_store_cross_replica_read_after_write` and `tests/test_exchange_store_port.py::test_exchange_store_cross_replica_read_after_write` (write via one adapter handle, read via a second, independent handle to the same backing store) — terminal-outcome parity alone doesn't catch a per-replica store, because it passes trivially single-process. Terminal-state writes (`completed/failed/canceled/rejected`) warrant retry + loud logging: a lost terminal write hangs the poller to its deadline, so it fails far louder than a dropped intermediate `working` write. See [runtime](runtime.md) (Cloud Run instance count / Gateway egress).

**Why the exchange store is a store we own.** The Exchange is a Bridge-invented aggregate with no managed GCP equivalent, so its GCP adapter is a store we own. It uses a relational store on both sides, so one implementation serves both local and deployed — queryable keys are indexed, flexible aggregate parts live in a document column. A record is keyed by `(kind, ref)` (e.g. `("rfp", <rfp id>)`), carries the exchange's A2A context token as an indexed non-unique column, holds the aggregate as a JSON document, and carries a version for compare-and-set writes: version 0 is create-only, any other expected version updates only if it still matches, and a mismatch is refused — that refusal is what keeps several replicas writing one shared table honest. The local adapter defaults to in-memory records (an async sqlite DSN makes them durable); the GCP adapter rides the shared Cloud SQL DSN and refuses an in-memory fallback (the session-affinity trap above). The store's API is synchronous — its callers apply "fresh read → apply → write" with no suspension point in between — over an async engine running on a private loop thread, since only async database drivers are in play. A managed relational upgrade path exists with no rewrite.

**Why the skill registry format is the same on both sides.** Both adapters store the identical unit — an [Agent Skills](skills.md) folder (`SKILL.md` + `assets/`, agentskills.io). The local adapter is a directory of those folders; the GCP adapter is the managed GCP **Skill Registry** holding the same folders. Because the *format* is the port contract (not a store-specific schema), a skill authored once installs unchanged locally and deployed, the Agent Card is generated from the same `name`/`description` either way, and one parser gates both — the Bridge's loader reads each folder's `SKILL.md` frontmatter into `SkillMeta` and refuses a folder missing `name`/`description`/`bridge-kind` or carrying an invalid `bridge-hitl`, identically on both adapters — a malformed folder is skipped (logged) by both adapters' listing and refused by both adapters' install, before any write ([bad uploads](skills.md#bad-uploads-are-refused-not-propagated)). Moving to the managed registry is a storage swap, not a re-authoring.

**Why email ingress is a port.** Inbound email is a new external boundary — an M365 mailbox fed through Microsoft Graph into a landing zone — not a native backend swap like the artifact store or host glue like the portal store, so it gets the full port treatment ([email intake](email-intake.md)). The port is the **landing zone**, not Graph: `land` / `pending` / `read` / `put_attachment` / `mark_processed` / `processed` over one object layout (`inbox/<key>.eml`, `attachments/<key>/<index>/<filename>`, `processed/<key>.json`). Every write is **create-only** on both sides — a temp file published with a hard link locally, `if_generation_match=0` on GCS — so landing doubles as the idempotency check (a Graph re-delivery is a duplicate) and the inbox minus the processed markers is the queue. The Graph client is the deployed *transport* into `land`; its local analogue is an operator CLI that lands an `.eml` file.

**Why extraction is a port — and why more than one engine.** Extraction is [covered by dedicated services](bridge.md), so the Bridge refuses to marry one engine. The extraction service returns normalized fields plus per-field and overall confidence, legibility, and flagged fields; [disposition](disposition.md) reads those signals **engine-agnostically**. The described engines are the **Gemini** adapter (schema-driven JSON, multimodal, ~$0.10 / 1k pages), a deterministic **fixture** adapter for fast tests, and the **Document AI** engine — the same schema-driven Gemini request with the client's existing Document AI processor run in front of it as an OCR / Layout / Form Parser [pre-pass](extraction.md#document-ai-pre-pass--the-docai-engine) (its data-residency / compliance posture is the client's own processor). Note the axis differs from the storage ports: the real engines are deployed either way, selected by deployment config (`BRIDGE_EXTRACTION_ENGINE`), not per doctype and not local-vs-GCP. A second engine behind the same port is the thesis made literal — mediation is the focus, extraction is delegated: swap the engine, the mediation around it never moves. **Why a pre-pass, not a parallel adapter:** Gemini takes an arbitrary schema and prompt from the doctype skill, while a per-doctype Document AI extractor would need a processor and an entity map bound per doctype — so Document AI contributes only what Gemini lacks, a machine-read text layer, and the doctype mapping stays in one place ([Document AI pre-pass](extraction.md#document-ai-pre-pass--the-docai-engine)). **The engines' input envelopes differ:** the Gemini engine takes *native-digital* documents — text SVG, images, and a **native-digital PDF** — as inline bytes under the schema the doctype skill pins, while a **scanned/raster PDF (OCR)** is the Document AI engine's envelope: the OCR text rides next to the document in the same request. That difference in what a document physically *is* — not just in per-field confidence or data residency — is a concrete reason the port exists.

**How a doctype binds an engine.** A doctype skill declares its Gemini binding — always present: the `SKILL.md` body plus the schema rendered from its OKF bundle ([ontology](ontology.md); `assets/schema.json` is the generated copy) — which **every** engine uses, the Document AI engine included: its pre-pass is doctype-agnostic (doctype is an output of extraction), so it reads the one processor configured for the deployment (`BRIDGE_DOCAI_PROCESSOR`, the client's processor by full resource name) and a doctype needs no Document AI binding to be read from a scan. The **optional** per-doctype key (`bridge-docai-processor`, plus a `docai-entity-map.yaml`) is reserved for a doctype-specific custom extractor and is not consulted by the pre-pass. Likewise `bridge-extraction-engine` is not read: the engine is set for the whole deployment (`BRIDGE_EXTRACTION_ENGINE`). The port **never hard-fails** on a doctype no processor covers. This is the doctype's capability envelope.

**The doctype schemas drive the request, through the port.** The Gemini engine does not carry a literal prompt. It reads every installed **doctype** through `bridge/doctypes.py::doctype_schemas` — the installed list from the `skill_registry` port, each schema rendered from the doctype's OKF bundle when one exists and otherwise read from its `bridge-schema` asset (`read_asset(name, rel)`, normally `assets/schema.json`) — never through a module-level cache (the skills root changes at runtime, so a process-wide cache would break the live skill-add property). The declared fields are rendered into the prompt as the installed-doctype catalog, and their **union** is pinned as the request's structured-output `response_schema`. Installing a doctype skill folder therefore changes extraction with **no code change and no redeploy** — the same property the Agent Card already has, now on the extraction path. A doctype whose declared asset is absent contributes its name only (a legitimate half-installed registry state must not kill all extraction); a present-but-unparsable asset refuses loud.

Two consequences of that union are load-bearing. `fields.doctype` is pinned as a **free string with no enum**: the Bridge *classifies* — `extract(artifact_name)` takes no doctype — so a document outside the installed label space (a passport) must stay reportable or the `unsupported` terminal outcome silently disappears. And because one document only ever carries one doctype's fields, every union property is nullable and none is required, so the parse **prunes null-valued** `key_fields`/`field_confidence` entries before validating (the wire types are `dict[str, str]` / `dict[str, float]`); the top-level `extra="forbid"` loudness is untouched. When no installed doctype declares fields, no `response_schema` is pinned at all — an empty-properties object would forbid every field.

**The engine's input is a resolved reference, not a filename.** Documents cross the wire [by reference](artifacts.md), so the string the port is handed is the counterparty's uri. One resolver turns it into the engine's input envelope — either **inline bytes** (a corpus name, or a party's `http(s)` URL fetched under a default-deny egress guard with every redirect hop re-validated) or a **native `gs://` pointer** the model reads itself, no download and no storage client on the Bridge side. The resolve happens **once per extraction, never per retry attempt**, and it refuses loud: an unreadable, refused or unsupported reference raises rather than degrading into a fixture (the same no-fabrication rule the retry obeys). The four shapes and the two-sided leg-scoping claim are in [artifacts](artifacts.md).

**The parse is the contract — schema-validated retry.** Because the extraction wire type is `extra="forbid"`, one stray key, one non-string field value or one truncated token rejects the whole payload — and a document that reached the engine must not be lost to a single malformed token. A rejected payload is therefore **re-asked up to three times**, each follow-up turn carrying the model's own rejected output *and* the specific validator reason (the echo is what makes the next attempt a repair rather than a re-roll, bounded so a runaway response cannot balloon the request). The doctype catalog, the resolved document bytes and the pinned schema are computed **once per extraction** and reused across attempts — a retry re-asks, it never re-fetches the artifact. On exhaustion the **last validation error is raised**, annotated with the attempt count and the artifact: there is deliberately **no fixture fallback** (it would launder hand-authored corpus values in as if they had been extracted) and **no silent success** — a missing extraction is a measurable miss, a fabricated one is a lie. Only validation and JSON-decode rejections retry: a transport/API error (429/500) is not a schema rejection, burns no attempt, and surfaces unchanged. The validator stays the retry's oracle, so it is never weakened into a tolerant reader to make a payload fit.

**Large documents — page-window chunking.** A carrier rate sheet can carry a thousand rows, and one structured response that size is cut at the output budget (`finish_reason == MAX_TOKENS`) — the *output*, not the input window, is what runs out, and re-asking at the same budget only reproduces the cut. So every request states an explicit `max_output_tokens` (a documented budget is what makes truncation detectable), a truncated response **never enters the schema retry** (it is not a malformed payload; echoing a cut body back would be futile), and the engine instead asks for less output per request. An inline PDF longer than `chunk_pages` pages (read with the standard library — no PDF dependency) is extracted as **page windows** up front; a truncated single call is **bisected by page** (a `gs://` object, whose page count the Bridge cannot see without downloading it, first gets one tiny page-count survey call). Each window request carries the **whole document** plus a window instruction — `[prompt, document, (ocr_context), window_instruction]` — because a by-reference object cannot be split without the download the resolver exists to avoid; input cost grows with windows × document tokens while the output that truncates is bounded per window. Windows run the same bounded schema-validated retry, concurrently (bounded) and under a hard per-extraction window cap, and every model call runs off the event loop so a slow call never stalls the hosts sharing it. The merge is **code-side and conservative**: table rows concatenate in page order with no dedupe (a dropped row is silent loss, a duplicate is visible to review), whole-document scalars take the first window's value and a later disagreement is flagged for review rather than overwritten, window-local row paths in flags/reviews/confidences are rebased onto the merged table (an index the window never emitted is coarsened to the whole table, never guessed), confidence is the minimum and legibility the conjunction. There is **no partial success**: any failed window fails the extraction with the original error, and a single page that alone overflows the budget raises a deterministic `ExtractionTruncated` (a `ValueError`) naming the page and the budget. A short document — every Address record, every one-page quote — is still exactly one call shaped `[prompt, document]`. Detail: [extraction feature notes](../docs/features/extraction.md).

GCP *write* paths (event publish, timer enqueue) assemble their requests on the deployed edge, sharing the same adapter contract as the rest of the port.

**Deploy.** A single deploy step packages the Bridge, provisions the runtime, and builds validated Gateway/Identity deploy specs. Every demo — including the Address warm-up — runs on this deployed path.

## Terraform: substrate primitives, not one-module-per-service

Terraform is organized **by GCP substrate primitive — what Terraform actually provisions — never one-module-per-platform-service.** The platform-native services are consumed through the ports (their GCP adapters are config + IAM + client code), which is exactly why none of them appears as a same-named Terraform module. The module set reads as generic Cloud Run + VPC + Cloud SQL + Cloud Tasks + Secret Manager + LB on purpose: **Terraform provisions substrate; the ports provision services.**

The module set: `network` (two subnets modelling the two trust zones + firewall isolation), `runtime` (Cloud Run v2, VPC egress, ingress computed from `enable_gateway`), `gateway` (toggleable external HTTPS LB → Serverless NEG), `iam` (the `bridge-runtime` workload SA + `cloudsql.client` / `cloudtasks.enqueuer` / `aiplatform.user` grants + the Cloud Tasks token-creator for OIDC callbacks), `database` (Cloud SQL Postgres 16 on private IP via Private Services Access), `tasks` (the `bridge-followups` queue), `secrets` (Secret Manager; the DB DSN rides a `DATABASE_URL` secret env, never plaintext), and `frontend` (the deployed surfaces). The `gcs` module homes the Skill Registry bucket and the Artifacts bucket. [Email intake](email-intake.md) is a delta across these modules, gated on `enable_email_ingress` (off by default): a webhook-only Cloud Run service in `runtime` running as its own create-only SA from `iam`, three Secret Manager containers in `secrets` (values added out-of-band), and a lifecycle-retained landing bucket in `gcs`. The landing bucket is drained by the RFP board host: a second internal-only Cloud Run service in `runtime` (gated on `enable_rfp_board`) running as `bridge-runtime`, whose `POST /email/drain` a Cloud Scheduler job calls with an OIDC token.

**`runtime` = Cloud Run v2 for the HTTP/webhook/REST edge + Agent Engine for managed Sessions, Memory Bank, ADK `App` execution (Option A), and the A2A Server (Option B).** Cloud Run serves the thin HTTP edge — custom HTTP routes outside the A2A JSON-RPC protocol (the A2UI portal endpoints, the scoped artifact-fetch endpoint `/artifacts/{context_id}/{name}`, the M365 Graph email intake webhook, the RFP board REST API, and the Address wake receiver `/wake`) and, when `BRIDGE_AGENT_ENGINE_A2A=1`, proxies `GET /.well-known/agent-card.json` and `POST /` (unary and SSE streaming A2A JSON-RPC 2.0) to `BridgeA2aAgentEngine` (`bridge/edge/agent_engine_a2a.py`) on Agent Engine. Agent Engine (`aiplatform.googleapis.com` `ReasoningEngine`) hosts the managed ADK `VertexAiSessionService`, `VertexAiMemoryBankService`, remote `document_bridge` / `address` ADK `App` execution (`BRIDGE_AGENT_ENGINE_ID`, `BRIDGE_AGENT_ENGINE_REMOTE=1`), and the A2A server runtime (`CollectExecutor` + `EdgeRequestHandler` + dynamic `AgentCard` via `BRIDGE_AGENT_ENGINE_A2A=1`), with a Private Service Connect network attachment (`enable_agent_engine_psc`) on the internal subnet.

**Durable state = Agent Engine (Sessions + Memory Bank) + Cloud SQL Postgres (Task store + Exchange store).** Behind the ports sit ADK `VertexAiSessionService` when `BRIDGE_AGENT_ENGINE_ID` is set (or `DatabaseSessionService` on `DATABASE_URL` when unset), ADK `VertexAiMemoryBankService` behind `Port.memory_bank`, a2a-sdk `DatabaseTaskStore` + push-config store (tasks), and the Bridge's `SqlExchangeStore` (exchange records) on Cloud SQL Postgres.

Adding a platform service in a later release grows a port adapter + a small Terraform delta, not a restructured module set — substrate-oriented modules are the stable base those deltas attach to. Validation is credential-free plan-time tests (`terraform test` + `mock_provider`); the deployed-path parity run is separate, against a provisioned project.

## Testing the ports — one shared suite, two adapters

Every managed-service port is verified by the **same test suite running against both adapters**, ensuring the mock→real and local→GCP swaps are **no-ops for the agent**. This is the parity claim that lets the Bridge develop at local speed while genuinely showcasing the managed platform.

**The ports.** The test markers enumerate all 14 `Port` enum names: `sessions`, `task_store`, `exchange_store`, `skill_registry`, `memory_bank`, `scheduler`, `a2a_client`, `extraction`, `email_ingress`, `audit_vault`, `operational_store`, `action_inbox`, `agent_gym`, `knowledge_catalog`.

**The harness:**
- **`adapter` fixture**: parametrized over `("local", "gcp")`. The `local` adapter **always** runs; the `gcp` adapter runs **only when `BRIDGE_TEST_GCP=1`** is set (skips otherwise, e.g. in CI without credentials). The *same* test body asserts both.
- **`@pytest.mark.port("<name>")` marker**: labels which port a test covers, using one of the names above. A collection-time guard asserts every marker uses a valid port name (no silent typos).
- **Single source of truth**: a `Port` enum defines the port names; the port Protocols/ABCs and their local and GCP adapter implementations sit behind it.

**Axis nuance:** Every port but extraction (`sessions`, `task_store`, `exchange_store`, `skill_registry`, `memory_bank`, `scheduler`, `a2a_client`, `email_ingress`) is a **local↔gcp storage/infra** port — the `adapter` fixture's axis. **Extraction is the capability axis** (`fixture|gemini|docai`), deployed either way; the real engines are selected by deployment config, not per doctype. Extraction is a port for marker + interface organization, but it doesn't parametrize the same way.

**Parity invariants** (enforced by the shared suite):
1. **Mock→real and local→GCP swaps are no-ops for the agent.** The consuming code (the service agents and the Bridge core) never keys off which adapter is active. The test suite runs the same assertions against both.
2. **Parity is terminal-outcome, not ledger-identical.** Mock and real adapters (and local vs. GCP) legitimately diverge turn-by-turn; parity tests assert the same *destination* — terminal reason + accepted-issuer set — never a step-by-step ledger match.

**Per-port override:** `BRIDGE_PORT_MODE=local|gcp` sets the global default; individual ports override via `BRIDGE_PORT_SESSIONS`, `BRIDGE_PORT_TASK_STORE`, etc. (blank = inherit from global). Extraction is its own axis: `BRIDGE_EXTRACTION_ENGINE=fixture|gemini|docai` (`fixture` default); `docai` also needs `BRIDGE_DOCAI_PROCESSOR` and refuses to run without it. The model engines share three integer knobs, read at construction (a malformed or out-of-range value refuses loud naming the variable): `BRIDGE_EXTRACTION_MAX_OUTPUT_TOKENS` (default 32768), `BRIDGE_EXTRACTION_CHUNK_PAGES` (default 8; `0` disables chunking, so a truncation fails at once) and `BRIDGE_EXTRACTION_CHUNK_CONCURRENCY` (default 4). Gemini extraction opts in via `BRIDGE_TEST_GEMINI=1`.
